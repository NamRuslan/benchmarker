# Benchmarker - Небольшая утилита для нагрузочного тестирования
Компилируется в исполняемый файл, запускается с консоли.

---
## Запуск
Запускается в консоли с указанием флагов. Подсказка по флагам выводится флагом -h.  
**Флаги (параметры запуска):**
* -b:  Использовать ли в запросе body . Если используется, нужно положить файл с готовым запросом body.txt рядом с exe файлом. Если это запрос GraphQL, в файл положить просто GraphQL query.
* -d:  int Длительность теста в секундах. (default 60)
* -debug:  Режим дебага. Выводит дополнительную информацию в консоль и сохраняет все в отдельный файл рядом с exe файлом.
* -gpath:  string Эндпоинт GraphQL. Если указан, скрипт будет искать запрос в файле body.txt рядом с собой и автоматически устанавливает method=POST. Пример: "/some-service/api/v1/graphql".
* -m:  string Метод запроса. Поддерживаемые варианты: GET, POST, PATCH, DELETE, PUT. (default "GET")
* -rc:  int Суммарное/предельное кол-во запросов, отправляемых по URL. (default 20)
* -rps:  float Количество запросов в секунду для ОДНОГО виртуального пользователя. Общий целевой RPS будет рассчитываться как rps * vu. (default 1)
* -sid:  string Хедер ID сессии. Будет добавлен к заголовку Cookie в виде sessionId=asd123qwe456
* -url:  string URL на который будут отправляться запросы. (default "http://localhost:8080")
* -vu:  int Кол-во виртуальных пользователей, столько клиентов будут отправлять запросы параллельно. (default 1)

**Пример для PowerShell:**   
`.\benchmarker.exe -gpath "/api-gateway/graphql" -sid asd123qwe456 -rps 5 -vu 10 -url "https://some-service.com" -debug -rc 100`

## Примечание для использования запросов с телом
Если указан флаг -gpath и/или -b, скрипт будет искать тело запроса в отдельном файле body.txt в той же папке, где и находится сам скрипт.  
Если используется graphQl запрос, в файл нужно вставить просто сырой (raw) graphQl - запрос, скрипт сам его обернет в нужный формат POST запроса.

## Примечание для работы в режиме debug
Если указан флаг -debug, то в консоль будет выводиться дополнительная информация по отдельным запросам, такая как тело ответа, время его получения и тд. Кроме того, скрипт создаст отдельный текстовый файл рядом с собой, куда будет продублирована дополнительная информация по запросам.

# Ключевые решения
* Для обеспечения действительного параллелизма отправки запросов от разных виртуальных юзеров, каждый из них работает в отдельный горутине.
* Также для обеспечения действительного RPS, каждый запрос так же отправляется в отдельной горутине, чтобы из-за синхронности один запрос не тормозил другой.
* У самого теста есть общий таймаут (по дефолту 60 сек, устанавливается флагом), через контекст он передается и всем отправляемым запросам, поэтому по его истечению, отправленные запросы не будут висеть и будут закрыты вместе с приложением.
* Сбор результатов. Результаты собираются в мапу "Результат ответа" - "Длительность", т.к. подразумевается что вариантов результата ответа не так много, было принято решение не использовать синхронную мапу или мьютекс, т.к. это скапливало бы горутины запросов в очередь и они накапливались бы в памяти. Кроме того, опять же из-за малого кол-ва ключей, постоянные блокировки по одному и тому же ключу или всей мапе только замедлили бы работу скрипта. Взамен, я выбрал буфферизированный канал с обычной, неблокирующей мапой. Отдельная горутина получает данные из канала и в одном потоке складывает результаты в мапу.
* Для синхронизации выполнения работы горутины вирутального юзера и горутины отдельного запроса используются разные WaitGroup. Главная горутина дожидается выполнения ВЮ, отдельный ВЮ дожидается окончания обработки запросов. WaitGroup для запросов используется для того, чтобы на момент окончания работы горутин ВЮ не осталось запросов "за бортом", чтобы не было ситуации, когда ответ по запросу еще не вернулся, а главная горутина уже закрывает канал результатов и начинает их обработку. Кроме того, каждая горутина ВЮ создает новый WG для запросов. Если объявить в главной горутине WG для запросов, может произойти сутуация, при которой главная горутина уже ждет WG запросов, а горутина запросов только увеличивает счетчик с 0 до 1, что приведет к ошибке.
